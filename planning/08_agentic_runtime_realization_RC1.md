# Realización agéntica PAPER candidata — RC1 / B-RT1

2026-10-07 · R-006/R-010/R-013 · D-024/D-027 **READY_FOR_DECISION de este diseño propuesto**, no permiso final, selección operacional ni prueba S2-B. ADR-011 A/ADR-012 S2-B/ADR-013 delimitan la propuesta. Cambios administrativos solo en target con gates futuros.

## 1. Procesos y ownership concretos

| Contexto | Realización candidata | Recursos y exclusiones |
|---|---|---|
| F — Financial Core | Proceso local determinístico bajo principal financiero confiable | Risk/Execution/financial DB/broker credentials. Nunca un SDK/modelo/agent tool dentro de F |
| C — Trusted Control | Scheduler/workflow, exporter, launcher/supervisor, admission y audit bajo principal confiable **distinto de Agent Runner A** | Job ledger/epoch/leases/receipts/config y exports. No heredar broker secrets/env. No ejecuta código/prompts/plugins generados por agentes ni entrega SQL/Temporal/admin a J |
| A — Agent Runner | Una identidad Windows estándar dedicada a runtime Codex, fuera de F/C | Login Codex legítimo propio, sin cuentas por rol. No heredar identidad/config del developer |
| J — native job | SDK Python oficial + CLI/app-server emparejado en **token A restringido por intento**, SID restrictivo único de contexto, sin privilegios adicionales | Paquetes/exports readonly, scratch/output propio; ningún estado C/F, peer, perfil completo o otro job. Todo proceso/descendiente conserva restricciones y lifecycle |

**B-RT1 usa restricted tokens Windows como realización principal a validar**, coherente con el laboratorio semántico/FS preparado. AppContainer no se selecciona en paralelo. Si el token no cumple aislamiento efectivo, registrar bypass/limitación y reevaluar S2-A o S3 con propietario; no elegir nueva realización silenciosamente. Pruebas target pueden invalidar B-RT1. Job Object controla lifecycle, no concede seguridad.

El supervisor no se coloca bajo A en esta realización. Ownership/DACL de procesos, tokens, handles, policy, exports y objetos IPC protegidos corresponde a C; J no hereda handles privilegiados, token C, WRITE_DAC/WRITE_OWNER o capacidades de impersonation. Identidades/SIDs/ACL reales se enlazan localmente en target y no se transportan por Git. C puede pertenecer al dominio confiable del core, pero sus interfaces/credenciales son distintas; crear un tercer principal OS C/F si fuera necesario sería un gate específico, nunca un usuario por rol.

**TokenPolicy B-RT1-T1:** token base A estándar verificado; grupos de acceso general/developer/admin no necesarios pasan a deny-only. TokenUser A permanece habilitado únicamente para compatibilidad native auth, sin que conceda acceso a namespaces privados por sí solo. Retirar todos los privilegios, incluido SeChangeNotify: `DISABLE_MAX_PRIVILEGE` solo no basta. Prohibidos WRITE_RESTRICTED, SANDBOX_INERT, SeDebug, SeImpersonate, SeAssignPrimaryToken o privilegios de recovery dentro de J. SID restrictivo único por attempt protege lecturas y escrituras; un SID común de runtime, si necesario, solo concede lectura/ejecución de assets públicos pinados y tránsito declarado, nunca exports/scratch/store privado. No Users/Everyone/shared-runtime grants en namespaces de jobs. Owners/DACL son C, no J. Comparar token efectivo con policy antes de launch; incompatibilidad de tránsito/runtime bloquea, no fallback a token A sin restricciones. El [counterexample common-SID](research/R-013_S2B_lab_preparation_2026-10-06.md) explica por qué la lista de SIDs sola no prueba aislamiento.

**Desktop/window station:** contexto no compartido con C/F ni peers, con DACL y ciclo de vida por attempt. Headless/CREATE_NO_WINDOW no sustituye este requisito. [Microsoft restricted tokens](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) advierte sobre ataques mediante mensajes en el desktop por defecto. Creación/permisos/compatibilidad efectivos quedan R-030, sin crear objetos ni cambiar políticas aquí.

**AcquireRunnerLaunchCapability:** entrada owner/C = identidad A verificada, policy/pin/grant autorizado y autenticación local segura del owner cuando se establece la sesión; salida = handle OS de launch de alcance A, no exportable a J/modelo/Git/logs. C conserva handle privado, lifetime de sesión/incarnation, revoca al terminar/invalidar; acquisition/reboot/refresh/revocación fallidos bloquean nuevos jobs. Familia primaria candidata `CreateProcessAsUserW` con token A restringido y atributos de seguridad/entorno/handle list explícitos. Crear un restricted token no adquiere por sí solo capacidad cross-user: [API y derechos](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw). El mecanismo seguro concreto para obtener ese handle y derechos mínimos de C se revisará en target; no seleccionar LocalSystem/servicio ni grant SeDebug/SeImpersonate tácitos. Inicializar o recuperar sesión puede requerir owner una vez; no aprobación/login por job rutinario. Si la realización exige supervisor bajo A, nuevo servicio privilegiado, password en scripts o autenticación humana por job, reabrir diseño/gobierno; no tratarlo como un parámetro de aceptación. Ningún setup administrativo está autorizado aquí.

## 2. Transporte y tools

Ruta candidata mínima: **Python Codex SDK low-level oficial**, que reutiliza app-server/CLI bundled; API de modelos facturada aparte inactiva. Baseline probado 0.160.0 SDK/CLI emparejados, por confirmar/pinar contra release target. Raw app-server solo si un gap documentado del SDK lo requiere. Un proceso/attempt efímero, sin reutilizar thread vivo entre roles; rehidratar desde manifest/snapshot, no chat histórico.

Perfil operacional inicial cerrado: shell/exec, file mutation, web/browser/computer-use, images arbitrarias, hooks, memories, goals/auto-continuation, recursive subagents, plugins/apps y MCP **inactivos**. La ausencia de flags/keys reconocidas o una herramienta extra impide launch; no asumir que apagar unified_exec apaga el shell. No exponer `process/*`, `command/exec`, `fs/*`, config/install/login/write APIs al modelo. Estos controles de producto complementan token/ACL/red; no los sustituyen.

Solo tools explícitas por rol y snapshot:

- `read_snapshot_section(section_id)` resuelve IDs fijados por C, sin path/URL/query SQL aportado por el modelo;
- `read_evidence_item(evidence_id)` solo IDs del manifest y clocks admitidos;
- `compute_registered_metric(metric_id, input_ids)` solo funciones determinísticas/versionadas y unidades declaradas; retorno con linaje, sin evaluación de expresiones/código;
- output estructurado final bajo schema/rol fijado por C. Ningún tool financiero, promoción, allocation, Risk/Execution, resume o order.

Callbacks del Python SDK **dentro de J son stubs sin privilegios**, no ejecutores trusted: solo serializan `READ_TOOL` al canal privado, con IDs fijados, y reciben una respuesta acotada. La operación sobre exports/métricas y validación pertenece a C, sin código generado por modelo. `SUBMIT_RESULT` es un mensaje distinto, no una tool capaz de escribir/admitir resultados. C impone tipos, rol, allowlist, cuota y binding desde su mapping; claims/IDs/permit strings de J nunca autentican al emisor. No endpoint genérico de SQL, paths, expresiones, launch, config o control. Estos adaptadores serían WRAP futuro de transporte oficial, no nueva implementación autorizada.

Los handlers de solicitud nativa son tipados: command/file/permission/network → denegar mediante respuesta válida del método; elicitation → decline/cancel; petición de owner input → registrar USER_ACTION_REQUIRED y terminar/pender el job, sin espera infinita; método desconocido/no representable → cerrar intento `RUNTIME_FAILED/PROTOCOL_UNSUPPORTED`. No default auto-approval. Dynamic tools experimentales requieren pin y regresión; si fallan, procedimiento mínimo con snapshot en input puede ser fallback **solo si conserva el contrato funcional**, no transferencia automática de selección ni permisos.

## 3. Auth y persistencia

Principal A tiene **únicamente autenticación nativa Codex** necesaria, introducida por propietario en interfaz oficial. Propuesta primaria de almacenamiento: `cli_auth_credentials_store=keyring`, sin fallback `auto/file`, API key ni tokens externamente gestionados. Compatibilidad Windows/keyring/restricted-token/refresh **NOT_TESTED**; no se hace login aquí. No pedir nuevas credenciales por cada job; refresh/revocación/cuota produce estados explícitos. Si keyring no es viable, presentar diseño de auth alternativo al owner antes de cambiarlo.

El runtime nativo necesita su auth de modelo; eso no autoriza exponerla a outputs, tools o peers. Tools iniciales no incluyen shell, filesystem genérico ni credential APIs; sus handlers están fuera del modelo y solo leen exports permitidos. Token/handles/memory/client process y store de auth requieren negative tests separados. Si una herramienta/bypass alcanza auth fuera del mínimo declarado, B-RT1 falla hasta reparación. No se afirma que keyring o mismo SID separe roles por sí solo; no hay secretos financieros en A/J.

No asumir CODEX_HOME diferente por intento con keyring compartido: el código oficial pinado 0.160 deriva la clave keyring de la ruta canónica de CODEX_HOME. Una propuesta inicial con home nuevo por job habría requerido namespaces/login distintos; se corrige antes de aprobación. [Fuente pinada](https://raw.githubusercontent.com/openai/codex/rust-v0.160.0/codex-rs/login/src/auth/storage.rs).

Realización propuesta: **un CODEX_HOME de auth/config mínimo fijo bajo A, readonly para J y administrado por control/owner**, sin auth.json/file fallback, historia, memory, prompts, sessions o resultados de roles. Permite namespace keyring nativo estable sin copiar tokens ni construir auth broker. `sqlite_home`/CODEX_SQLITE_HOME y `log_dir`, cwd/workspace/TEMP/scratch/output se redirigen a ubicaciones privadas por intento, creadas/controladas por C; history.persistence=none, thread ephemeral, hooks/memories/shell_snapshot/goals inactivos. J no puede escribir el home común ni leer stores/logs de otros jobs. No home general del propietario.

Estos redirects no afirman que TODO cache/write nativo esté cubierto. C inventaría accesses reales; cada write residual al home común debe estar denegado, ser innecesario o tener ruta permitida por job explícita. Si native runtime requiere persistencia compartida de contenido de jobs, la realización falla hasta revisión; no grant RW al home común ni login por job como reparación automática. Cache común permitido solo metadata/config sin contenido excluido, versionado y revisado. Canary→relaunch debe negar material Champion/peer aunque el namespace auth sea estable. Auth propia mínima es persistencia autorizada; outputs/research se conservan mediante C y reexport explícito. Código/config no mutable por J; SDK/CLI y dependencias son assets confiables pinados, no código model-generated.

**BL-AUTH:** WinCred es también carrier potencial entre attempts: [CredRead](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw) usa la credential set de la logon session y requiere User SID habilitado. Un SID restrictivo diferente no demuestra namespace de keyring separado. Canary→relaunch debe incluir entradas arbitrarias/metadata no-auth del store compartido, además de filesystem/history. Solo auth native mínima es excepción autorizada; almacenamiento o recuperación de contenido de otro job mediante keyring/logon session es FAIL de blinding, incluso si tools no incluyen credential API. No se ha observado bypass real ni se ha probado compatibilidad. Si acceso requerido para refresh permite ese carrier y no puede bloquearse técnicamente, reevaluar S2-A/S3 o auth/trust realization con owner. No repararlo borrando canaries, instrucciones, nuevas credenciales por job o degradación de amenaza.

## 4. Canal autenticado y admisión

No endpoint de control global accesible al modelo. C crea canales privados por intento y conserva mapping **fuera de J**: process/token descriptor, `job_id`, `attempt_id`, generation, environment incarnation, snapshot/hash, rol/schema y deadline. Stdio transport de app-server queda dentro de J; C recibe la salida del launcher/supervisor mediante canal privado acotado. Solo handles IPC mínimos intencionales C↔J son transferidos al proceso J previsto: direcciones read/write y lista de herencia explícitas, sin acceso a otro peer, creación de server, duplicación o impersonación. Todos los demás handles C/F/token/supervisor son no heredables e inaccesibles. Sin endpoints TCP públicos o autenticación por username común.

Binding de recepción: C conoce el canal creado y su proceso/contexto de destino; no acepta IDs, rol, SID o epoch declarados por el JSON como identidad. Revalidar peer/contexto/lifecycle y la entrada de registro vigente antes de admitir. Un mensaje de otro canal, un attempt cancelado/expirado, proceso sustituido, handle duplicado o manifiesto distinto se rechaza/audita. No ejecutar código recibido. Límites bytes/campos/eventos/timeouts configurados en policy; valores finales D-025/028 con workload, no ilimitados.

**Job ledger C** es autoridad de workflow/admission, separado de DB financiera F. Manifest/outbox se confirman antes de launch. Lease/current_attempt/generation/expiry/lifecycle/incarnation + unicidad receipt se comprueban y actualizan en **una transacción de ese ledger**. Blobs sellados se escriben bajo C antes de confirmar su receipt; un blob sin receipt no es output admitido. Dos stores sin transacción conjunta no sustituyen este contrato. Collector conserva raw attempts/reasons y vincula linaje; hash no autentica al escritor.

D-025 motor y D-026 store siguen P1 transversales abiertos. Temporal/APScheduler o PostgreSQL/SQLite pueden compararse, pero solo candidatos que preserven este ownership y transacción son equivalentes para este contrato. Si elección mueve auth/launcher/admission dentro de agente o cambia autoridad/trust/recovery, reabre D-024/D-027 y necesita gobierno material. Redis/cache/OS timer no son autoridad de fencing/receipts.

## 5. Roles, carga y fallos

Research y Quant son advisory/research; no completan reglas operativas ausentes ni promueven Champion. Shadow y Pedagogy son capacidades requeridas por DoD PAPER, sin autoridad financiera. Shadow recibe snapshot pareado ciego, sin decisiones contemporáneas del Champion; Pedagogy puede recibir ledger factual posterior autorizado. Contratos 06 gobiernan evidence/lineage/no-output/late/unpaired; roles son fijados por C, no por JSON/modelo.

Ningún job es dependencia financiera de Strategy V1 **por esta arquitectura**. Si la estrategia necesita un input agéntico obligatorio, debe aprobarse contrato de freshness/failure y modo seguro antes de su selección. Un timeout/no-output no es HOLD ni orden alternativa. Fallo agéntico no reanuda pausa financiera ni autoriza G3; falla cobertura funcional según policy, con historial y escalamiento.

Scheduler admite jobs determinísticos por evento/calendario automáticamente. Cola/budget/deadlines/retries son finitos y versionados. Background no preemptivo puede bloquear Shadow (H3); prioridad de cola sola no basta. Antes de ventanas pareadas conocidas, reservar tiempo y no iniciar background incompatible; vencidos se registran, no se actualiza snapshot ni deadline para ocultar atraso. Concurrencia >1 necesita blinding/isolation/capacity de cada contexto y compartición auth probados; configuración inicial target se determina con R-030/Strategy workload, sin asumir cuota ni seguridad. No aprobar ahora números de retry/cadencia/SLO.

Upgrade: SDK/bundled CLI exactos, schemas/Skill/assets/config por Git hashes + runtime fingerprint, no latest implícito. No pin de pesos remotos por alias del modelo. Drift de versión/modelo/tools/config/policy invalida pruebas afectadas; actualizaciones requieren regresión y scope review, nueva aprobación si cambia arquitectura/autoridad/coste. No autoupdate operacional sin procedimiento aprobado.

## 6. Gates y límites

Diseño candidato concreto permite review/decisión sin ejecutar Plus o administración INFOTEP. R-030 verifica full-process/native tool policy/auth/keyring/IPC/FS/egress/blinding/relaunch/recovery bajo B-RT1. El lab FS histórico es una parte mínima, **no prueba** la nueva realización.

Antes de afirmar `AGENTIC_ARCHITECTURE_DESIGN_COMPLETE`: owner revisa esta realización material propuesta y revisión independiente sin hallazgos P0/P1 de diseño abiertos. D-024 freeze/operación no se cierran por el documento. Antes de implementar: target acceptance y DoR; después de construir: integración/carga/PAPER. LIVE UNKNOWN. No usuarios/ACL/policy/login/gasto o sistema productivo creados.

Tests específicos B-RT1 en R-030: positivo login/refresh native keyring desde el contexto permitido sin copiar secrets; negativo tool/peer/process-memory/credential-store fuera del mínimo; scope de todas las tools/features efectivas, inyección que pide shell/file/hooks/installer; homedir readonly + redirects per-job positivos/negativos; acceso peer/Champion canary tras restart; canal wrong-context/attempt/pid/epoch y duplicación de handles; C ledger receipt race/restore. Sin estas pruebas no KEYRING_ACCEPTED, ISOLATION_ACCEPTED o PAPER_RUNTIME_ACCEPTED. La experiencia de namespace auth se investiga en source ahora, el comportamiento efectivo pertenece al target.
