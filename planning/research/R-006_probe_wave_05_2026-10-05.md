## 1. MCP local: reutilizar protocolo, no inventarlo

Fuente primaria [SDK oficial MCP Python](https://github.com/modelcontextprotocol/python-sdk), licencia MIT. Paquete descargado gratuitamente a `%TEMP%/r006-mcpdeps`, versión observada **2.3.0**, Python **3.14** local; API de esta versión `MCPServer/Client`. Probe `stdio` con una sola tool `read_evidence`, fixtures wave 04 y dos procesos nuevos sucesivos. Sin modelo, datos remotos ni host Codex conectado a este servidor.

**13/13 checks pasan**: tool de lectura única, hint read-only, lectura exitosa, `place_order` inexistente rechazado, bundle inexistente rechazado y fallo de lectura comunicado en cada proceso; payload idéntico después de reiniciar el mock. Se conservan fuentes/clocks y texto malicioso como datos; **el protocolo no elimina inyección ni garantiza PIT**. La anotación `read_only_hint` es información declarativa, no control de permisos. El rechazo de órdenes surge de no existir tal herramienta en este mock.

**Fricción real de integración:** el primer import después de `pip --target` falló con `pywintypes` no encontrado en Windows. Se resolvió activando rutas temporales pywin32 y su directorio de DLL, sin postinstall global. Compatibilidad observada de este probe, no de un conector comercial ni broker. Excepciones sintéticas esperadas se observaron en stderr del SDK y no se guardaron raw en repo. Licencia MIT del protocolo no da derechos sobre datos.

[Código](probes/r006-behavioral-team/mcp_mock_probe.py) y [resultado](probes/r006-behavioral-team/mcp-result.json). Recomendación provisional: `WRAP` de una lectura ya admitida si hace falta interoperabilidad MCP; no construir un protocolo propio. Para el primer workflow, la tool dinámica mínima de wave 04 ya funciona; MCP no demostró calidad incremental del output ni integración Codex/Plus. No es obligatorio incorporarlo. Autenticación, permisos, PIT real, cadencia y costes del proveedor se prueban por conector finalista después.

## 4. Experimento de schema por rol tras el hallazgo wave 04

Se aplicó `jsonschema` a los outputs ya obtenidos, sin repetir conducta ni modificar retrospectivamente la rúbrica preregistrada. El schema genérico admitía **20/20**; un prototipo elegido desde **rol del llamador confiable** admite **17/20**: rechaza la propuesta INVESTIGAR en research y los dos roles traducidos de los fallos. El modelo no elige su validator a través de `role`. Cuatro mutaciones sintéticas de un output shadow se rechazan: mode operativo, autoridad de órdenes, campo TradeIntent añadido, role incompatible. [Código](probes/r006-behavioral-team/role_admission_probe.py), [resultado](probes/r006-behavioral-team/role-admission-result.json).

Esto demuestra discriminación estructural en un probe. **No** demuestra imposibilidad de shadow→ejecución en producción, no revisa texto malicioso semánticamente ni permisos/secretos reales. Deben completarse D-027 y D-034 y mantener un canal de órdenes separado con controles determinísticos. No congelar el schema de este experimento como contrato PAPER.
