## Build vs. Reuse

El **cliente oficial tipado de bajo nivel** cubre Skills inputs/discovery, dynamic tool callbacks, structured outputs y turn notifications en este probe. No se necesita construir transporte JSON-RPC propio para estas capacidades. C-029/C-025a se proponen WRAP dentro de una familia; no dos runtimes obligatorios. High-level SDK no recibió esta misma prueba callback y no se afirma equivalencia TS/Python.

Dynamic tools son **experimentales** según [app-server oficial](https://learn.chatgpt.com/docs/app-server); fijar versiones y regression de upgrades. El SDK utiliza app-server local y runtime pinado por defecto; override CLI debe ser explícito según [SDK oficial](https://learn.chatgpt.com/docs/codex-sdk). No congelar versión alpha como runtime producción por haber pasado este fixture.

## Seguridad y fallo del SDK por defecto

Inspección y llamadas offline al código público wheel pinado 0.160.0 comprueban que `_default_approval_handler` responde `accept` a command/file approval. Handler explícito del probe responde `decline`, tool exacto/límite 2, y rechaza desconocidos. No se ejecutó ningún comando solicitado. La [documentación de approvals](https://learn.chatgpt.com/docs/app-server) define esas decisiones; el default no es apto para REUSE_AS_IS de estos jobs.

La combinación permite comparar conducta con tool sintética; no demuestra aislamiento OS/secretos/network de todos los métodos ni ausencia de hooks/config heredados. [Contrato candidato de jobs](R-006_native_job_boundary_RC0.md) fija obligaciones/gaps antes de seguridad/freeze. `authority=NONE` y prompts no son ACL.
